# 燃气专题语义建模建议（临时）

## 1. 总体结论

当前系统更标准的语义建模逻辑是：

- **视图 = 基础数据宽表 / 业务明细视图**
- **维度 = 从视图字段里配置分析角度**
- **指标 = 从视图字段里配置聚合口径**
- **问数时 = 选择一个视图上下文，然后基于该视图上的指标、维度生成 SQL**

因此，Excel 中 `ddcat` 列里的 SQL 更像老系统的大屏卡片统计 SQL，不建议直接整体建成最终统计视图。推荐拆成：

```text
Excel 原 SQL 口径
        ↓
基础视图：整理字段、连表、统一字段名
        ↓
指标/维度：表达 COUNT、过滤、分组、比率
        ↓
问数 / 生成接口：按视图上下文输出结果
```

## 2. 字段来源说明

下文字段按以下规则标注：

| 标记 | 含义 |
| --- | --- |
| 已确认 | 字段名直接来自 Excel 中 SQL |
| 建议确认 | 字段名不是 Excel SQL 明确出现，但建模通常需要，需以现场同步后的真实字段为准 |
| 推导字段 | 由 SQL 表达式或字典映射生成，不是原表字段 |

# 4. 视图字段明细

## 4.1 `gas_enterprise_base_view`：燃气企业基础视图

### 4.1.1 涉及物理表

| 表名 | 用途 |
| --- | --- |
| `mf_gas_enterprise` | 燃气企业主表 |
| `mf_gas_employee` | 企业从业人员表 |

### 4.1.2 建议关联关系

主表建议使用 `mf_gas_enterprise`。这里要保留没有员工记录的企业，否则“燃气企业数”会被低估，所以用 `LEFT JOIN`。

| 主表 | JOIN 类型 | 关联表 | 关联条件 | 说明 |
| --- | --- | --- | --- | --- |
| `mf_gas_enterprise` | `LEFT JOIN` | `mf_gas_employee` | `mf_gas_employee.company_id = mf_gas_enterprise.id` | 保留所有企业；员工表只用于统计从业人员 |

建议 SQL 形态：

```sql
FROM mf_gas_enterprise e
LEFT JOIN mf_gas_employee emp
  ON emp.company_id = e.id
```

### 4.1.3 建议视图字段

| 建议视图字段名 | 来源表 | 来源字段 | 状态 | 用途 |
| --- | --- | --- | --- | --- |
| `enterprise_id` | `mf_gas_enterprise` | `id` | 已确认 | 企业唯一标识、企业数去重 |
| `enterprise_deleted` | `mf_gas_enterprise` | `deleted` | 已确认 | 企业有效性过滤：`deleted = 0` |
| `enterprise_business_status` | `mf_gas_enterprise` | `business_status` | 已确认 | 企业经营状态过滤：`business_status <> 3` |
| `employee_company_id` | `mf_gas_employee` | `company_id` | 已确认 | 员工关联企业 |
| `employee_delete_flag` | `mf_gas_employee` | `delete_flag` | 已确认 | 员工有效性过滤：`delete_flag = 0` |
| `employee_id` | `mf_gas_employee` | `id` | 建议确认 | 从业人员去重统计；如果无该字段，可用行数统计 |
| `enterprise_name` | `mf_gas_enterprise` | `name` / `enterprise_name` | 建议确认 | 企业名称维度，需按真实字段确认 |
| `enterprise_credit_code` | `mf_gas_enterprise` | `credit_code` / `qytyxydm` | 建议确认 | 统一社会信用代码维度，需按真实字段确认 |

### 4.1.4 建议指标

| 指标名称 | 指标展示名 | 来源字段 | 聚合 | 固定过滤 |
| --- | --- | --- | --- | --- |
| `gas_enterprise_count` | 燃气企业数 | `enterprise_id` | `COUNT_DISTINCT` | `enterprise_deleted = 0`、`enterprise_business_status <> 3` |
| `gas_employee_count` | 从业人员数 | `employee_id` | `COUNT_DISTINCT` 或 `COUNT` | `employee_delete_flag = 0`、`enterprise_deleted = 0` |

## 4.2 `gas_pipeline_inspection_base_view`：天然气管网巡检基础视图

### 4.2.1 涉及物理表

| 表名 | 用途 |
| --- | --- |
| `bm_facility_natural_gas_pipe` | 天然气管线表 |
| `ods_ng_pipeline_inspection_point_attr` | 天然气管线巡检点属性表 |
| `ods_ng_pipeline_inspection_attr` | 天然气管线巡检详情表 |

### 4.2.2 建议关联关系

主表建议使用 `ods_ng_pipeline_inspection_point_attr`。这张表代表巡检点，是覆盖率、巡检点数等指标的核心粒度。管线表和巡检记录表都建议 `LEFT JOIN`，这样可以保留“还没有匹配管线类型”或“还没有巡检记录”的巡检点，方便统计覆盖率分母。

| 主表 | JOIN 类型 | 关联表 | 关联条件 | 说明 |
| --- | --- | --- | --- | --- |
| `ods_ng_pipeline_inspection_point_attr` | `LEFT JOIN` | `bm_facility_natural_gas_pipe` | `ods_ng_pipeline_inspection_point_attr.fk_gx_id = bm_facility_natural_gas_pipe.id::varchar` | 保留所有巡检点；管线表提供 `gxlx` 管线类型 |
| `ods_ng_pipeline_inspection_point_attr` | `LEFT JOIN` | `ods_ng_pipeline_inspection_attr` | `ods_ng_pipeline_inspection_point_attr.id::varchar = ods_ng_pipeline_inspection_attr.fk_xjjl_id` | 保留无巡检记录的巡检点，用于覆盖率分母 |

建议 SQL 形态：

```sql
FROM ods_ng_pipeline_inspection_point_attr p
LEFT JOIN bm_facility_natural_gas_pipe pipe
  ON p.fk_gx_id = pipe.id::varchar
LEFT JOIN ods_ng_pipeline_inspection_attr r
  ON p.id::varchar = r.fk_xjjl_id
```

如果可视化表关联页面不能表达 `::varchar`，该视图建议使用 SQL 基础视图，但 SQL 仍应输出明细字段，不要输出最终统计卡片结果。

### 4.3.3 建议视图字段

| 建议视图字段名 | 来源表 | 来源字段 | 状态 | 用途 |
| --- | --- | --- | --- | --- |
| `user_id` | `mf_gas_nonresident_user` | `id` | 建议确认 | 用户去重统计；如果无该字段，可用行数统计 |

| `user_enterprise_id` | `mf_gas_nonresident_user` | 待确认 | 建议确认 | 所属企业维度 |
| `user_region_code` | `mf_gas_nonresident_user` | 待确认 | 建议确认 | 区域维度 |
| `user_created_time` | `mf_gas_nonresident_user` | 待确认 | 建议确认 | 时间维度 |

### 4.3.4 推导字段建议 SQL

```sql
CASE gas_type
  WHEN '管道天然气' THEN '天然气'
  WHEN '瓶装液化气' THEN '液化气'
  ELSE gas_type
END AS gas_type_mapped
```

### 4.3.5 建议维度

| 维度名称 | 显示名称 | 来源字段 |
| --- | --- | --- |
| `gas_type` | 气源类型 | `gas_type_mapped` |
| `resident_type` | 用户类型 | `is_resident` |
| `user_enterprise` | 所属企业 | `user_enterprise_id` |
| `user_region` | 区域 | `user_region_code` |

### 4.3.6 建议指标

| 指标名称 | 指标展示名 | 来源字段 | 聚合 | 固定过滤 |
| --- | --- | --- | --- | --- |
| `resident_user_count` | 居民用户数 | `user_id` | `COUNT_DISTINCT` 或 `COUNT` | `user_deleted = 0`、`is_resident = 1`、`gas_type IN ('管道天然气','瓶装液化气')` |
| `nonresident_user_count` | 非居民用户数 | `user_id` | `COUNT_DISTINCT` 或 `COUNT` | `user_deleted = 0`、`is_resident = 0`、`user_business_status IN (1,2)`、`gas_type IN ('管道天然气','瓶装液化气')` |

#### 4.3.7 固定过滤配置注意事项

`gas_type IN ('管道天然气','瓶装液化气')` 在平台指标固定过滤中应保存为数组值，而不是逗号拼接字符串。推荐接口形态如下：

```json
{
  "operator": "AND",
  "conditions": [
    { "field": "deleted", "op": "=", "value": "0" },
    { "field": "is_resident", "op": "=", "value": "1" },
    { "field": "gas_type", "op": "IN", "value": ["管道天然气", "瓶装液化气"] }
  ]
}
```

页面验收时应看到两个完整标签：`管道天然气`、`瓶装液化气`。如果页面显示为“管 / 道 / 天 / 然 / 气 ...”这类逐字标签，说明前端回填链路把数组误转成了字符串，应先修复回填逻辑再继续配置。

# 6. 单次对话只能选一个视图时的建议

当前系统更适合：

```text
一次问数围绕一个业务主题视图
```

例如：

- 问企业和人员：选 `gas_enterprise_base_view`
- 问用户分布：选 `gas_user_base_view`
- 问巡检覆盖率：选 `gas_pipeline_inspection_base_view`
- 问物联设备：选 `iot_equipment_base_view`

不要强行把所有燃气专题做成一个超级宽视图，因为这些表粒度不同：

```text
企业粒度
员工粒度
用户粒度
巡检点粒度
巡检记录粒度
安检记录粒度
设备粒度
```

强行合成一个视图容易产生重复计数，指标会不准。

# 7. 实施顺序建议

1. 同步物理表。
2. 先创建 5 个主题基础视图。
3. 在视图字段里补充展示名、字段说明、是否可过滤。
4. 配置维度。
5. 配置基础指标。
6. 配置复合指标。
7. 用问数验证每个主题视图。
8. 如需要大屏综合接口，再通过生成 API 或后端接口编排多个主题查询结果。
