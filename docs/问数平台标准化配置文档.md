# 问数平台标准化配置文档

## 1. 文档目的

本文档面向行业线业务对接人员、实施人员和现场工程人员，用于统一问数平台的数据接入、语义建模、模型配置和接口生成的配置口径，降低实施差异，提升上线效率。

适用目标：
- 新行业线数据接入
- 现场项目初始化配置
- 语义层资产梳理与验收
- 查询结果生成接口的标准化交付

---

## 2. 适用范围

当前平台已具备以下实际能力：

| 模块 | 当前能力 |
|------|------|
| 数据源管理 | 支持 PostgreSQL、MySQL、ClickHouse、瀚高 HighGo、达梦 Dameng |
| 物理表管理 | 支持同步物理表和字段信息 |
| 指标管理 | 支持基础指标、派生指标、复合指标 |
| 维度管理 | 支持普通、时间、地理、分类、数值维度 |
| 视图管理 | 支持单表、多表聚合、自定义 SQL 视图 |
| 字典管理 | 支持手动配置、引用视图、自动生成 |
| 模型配置 | 支持多供应商模型配置、测试连接、设为默认 |
| 问数配置 | 当前支持时间格式化配置 |
| 查询结果封装接口 | 支持输出格式配置、接口生成、接口调试、重新生成 |

---

## 3. 标准实施顺序

建议实施顺序如下：

1. 配置模型
2. 配置数据源
3. 同步或新增物理表
4. 配置视图分类和视图
5. 配置维度
6. 配置指标
7. 配置字典
8. 配置时间格式等系统参数
9. 执行问数验证
10. 如有对外对接需求，再生成接口并联调

> 如果项目数据结构较复杂，建议先完成视图建模，再开展指标和维度配置。

## 5. 数据源配置标准

### 5.1 必填与校验要求

| 字段 | 要求 |
|------|------|
| 数据源名称 | 必填，建议体现业务域与环境，如“城管上报库-生产” |
| 数据库类型 | 必填，仅选择实际支持的数据库类型 |
| 主机地址 / 端口 | 建议填写真实可达地址，不建议依赖默认值长期使用 |
| 用户名 / 密码 | 使用具备只读权限或最小必要权限的账号 |
| 数据库名 | 必填，必须与实际库名一致 |
| Schema | PostgreSQL / 瀚高可选填；瀚高不填时默认使用与数据库名相同的 Schema，若现场表在 `public` 或其他 Schema 必须显式填写 |

### 5.2 命名建议

建议命名格式：`业务域-系统名-环境`

示例：
- `城管-事件库-生产`
- `应急-指标库-测试`

### 5.3 验收标准

- 数据源创建后必须执行一次“测试连接”
- 列表状态应为“正常”
- 至少完成一次物理表同步验证

## 6. 物理表配置标准

### 6.1 配置要求

| 项 | 标准要求 |
|------|------|
| 数据集名称 | 使用业务可理解名称，如“事件上报明细表” |
| 物理表名 | 与数据库真实表名一致 |
| Schema | 按数据库实际配置填写 |
| 字段信息 | 优先通过“同步物理表”或“从数据源同步”获取，减少手工错误 |
| 描述 | 说明表用途、主键、时间字段、状态字段等关键信息 |

### 6.2 字段治理建议

- 物理表同步为后台任务，实施人员应等待同步完成后再继续配置视图、维度、指标或字典
- 大表量数据源的物理表列表采用分页加载，查找非首屏表时应使用表名搜索
- 指标、维度、字典和视图设计器中的物理表选择框支持输入表名远程搜索，不要求一次性加载全量物理表
- 字段名称保持原库一致
- 如字段含义不清，需在备注中补充说明
- 时间字段、主键字段、状态字段、组织字段应优先梳理
- 供问数使用的表应尽量避免无意义缩写字段
- 如计划做跨表分析，建议在进入视图建模前先完成关键表和关键字段治理

---

## 7. 维度配置标准

### 7.1 命名标准

| 字段 | 建议 |
|------|------|
| 维度名称 | 使用英文或拼音标识，建议小写下划线风格，如 `street_name` |
| 显示名称 | 使用业务中文名称，如“街道名称” |
| 同义词 | 补充业务常见叫法，如“街道”“镇街” |

> 维度既可以来源于物理表，也可以来源于已配置完成的视图。对于跨表分析场景，建议优先基于视图配置维度，避免重复处理关联逻辑。

### 7.2 类型选择标准

| 维度类型 | 适用场景 |
|------|------|
| 普通 | 一般属性，如部门、街道、人员 |
| 时间 | 日期或时间字段 |
| 地理 | 省、市、区、经纬度等位置字段 |
| 分类 | 状态、类别、等级等枚举值 |
| 数值 | 适合做分段分析的数值字段 |

### 7.3 时间维度配置标准

- 必须指定默认格式
- 可选格式应来自系统已配置的时间格式列表
- 若后续需要按日、按月、按年分析，建议一次性配置完整

推荐最小配置：
- `YYYY-MM-DD`
- `YYYY-MM`
- `YYYY`

## 8. 指标配置标准

### 8.1 指标分类使用原则

| 类型 | 使用原则 |
|------|------|
| 基础指标 | 直接来源于表或视图聚合结果，优先使用 |
| 派生指标 | 用于固定时间口径或业务条件的常用分析 |
| 复合指标 | 用于多个指标之间的计算，如比率、差值 |

### 8.2 基础指标标准

- 优先使用“字段 + 聚合函数”方式配置
- 仅在聚合逻辑复杂时使用表达式
- 必须补充显示名称
- 建议填写业务口径与单位
- 如涉及时间分析，建议配置指标日期标识
- 如指标支持限定分析范围，建议配置分析维度
- 指标来源既可以是物理表，也可以是视图；跨表统计场景建议优先基于视图配置，保证口径稳定

### 8.3 派生指标标准

适用于以下场景：
- 近30天
- 本月/上月
- 同比/环比
- 固定状态筛选后的业务指标

建议：
- 时间限定和业务限定不要同时过度叠加，避免理解成本过高
- 派生指标展示名需直接体现业务口径，如“近30天上报量”
- 派生指标如果只是对基础指标增加固定业务过滤，应优先复用基础指标，并在固定过滤中表达业务范围，避免复制一套重复指标

### 8.4 指标固定过滤配置标准

指标固定过滤用于表达指标自身永远成立的业务条件，例如“有效数据”“居民用户”“特定气源类型”。固定过滤会随指标一起参与问数、MQL 转 SQL 和生成接口，不需要用户每次问数时重复说明。

配置要求：
- `=`、`!=`、`>`、`>=`、`<`、`<=`、`LIKE` 用于单值过滤
- `IN`、`NOT IN` 用于多值枚举过滤，值应保存为数组，例如 `gas_type IN ['管道天然气', '瓶装液化气']`
- `IS NULL`、`IS NOT NULL` 用于空值判断，不应再填写 value
- 同一指标存在多个固定条件时，默认使用 `AND`；确实存在多组条件时再使用嵌套 `OR`
- 过滤字段应优先使用语义字段名或视图字段名，避免在同一指标中混用展示名、物理字段名和源表字段名

常见示例：

```json
{
  "operator": "AND",
  "conditions": [
    { "field": "deleted", "op": "=", "value": "0" },
    { "field": "is_resident", "op": "=", "value": "1" },
    { "field": "gas_type", "op": "IN", "value": ["管道天然气", "瓶装液化气"] }
  ]
}
```

现场验收时，建议打开指标编辑弹窗核对过滤条件回显：
- `IN / NOT IN` 应显示为多个完整标签，而不是把字符串逐字拆开
- 保存后再次查询指标接口，`value` 应仍为数组
- 问数生成 SQL 时，`IN` 条件应渲染为数据库方言支持的多值条件

### 8.5 复合指标标准

- 表达式中引用的基础指标必须已稳定可用
- 复合表达式应可被业务人员理解
- 展示名称需体现业务意义，如“处置率”“客单价”

## 9. 视图配置标准

### 9.1 能力边界

当前系统中，视图是物理表之上的语义中间层，主要用于统一跨表分析口径、整理字段语义，并为维度、指标、字典、问数和生成接口提供稳定的数据来源。

当前能力边界建议按以下口径理解：

| 视图类型 | 后端能力 | 当前前端常用操作口径 | 建议场景 |
|------|------|------|------|
| 单表 | 支持 | 当前文档不作为主要页面操作流程展开 | 单张表即可满足分析需求 |
| 多表聚合 | 支持 | 支持可视化设计、拖表、连线、字段配置、预览 | 指标与维度分布在多张表，需要统一业务口径 |
| 自定义 SQL | 支持 | 支持 SQL 编辑、预览、保存 | 复杂逻辑无法通过简单拖拽快速表达 |

> 为避免文档写过头，现场操作手册与标准化配置口径以当前前端常用的“多表聚合”和“自定义 SQL”视图为主，不把后端存在但前端未完整展开的能力描述成标准页面流程。

### 9.2 配置前提与命名标准

视图配置前，应至少满足以下条件：
- 数据源已创建并测试连接成功
- 关键物理表已同步或录入完成
- 主键、时间字段、状态字段、组织字段等关键字段已完成基本梳理

命名建议：

| 项 | 建议 |
|------|------|
| 视图名称 | 使用英文或拼音标识，建议小写下划线风格，如 `event_summary_view` |
| 显示名称 | 使用业务人员易理解的中文名称，如“事件汇总视图” |
| 分类 | 按行业域、业务专题、对外服务对象等方式组织 |
| 描述 | 说明视图用途、涉及表、主要连接关系、适用指标口径 |

### 9.3 分类与交付标准

- 视图建议按分类树管理，不建议全部堆积在“未分类”状态
- 未分类视图可用于临时调试，但不建议作为长期交付结果
- 一个业务专题至少明确一个主视图，便于后续配置维度、指标与默认查询入口
- 对外交付时，建议输出“视图清单 + 分类说明 + 每个视图用途”

### 9.4 视图设计标准

#### 9.4.1 多表聚合视图

建议按以下顺序配置：
1. 选择数据源
2. 拖入需要参与分析的物理表
3. 配置表之间的 JOIN 关系
4. 选择并整理需要保留的字段
5. 补充视图名称、显示名称、分类和描述
6. 执行预览，确认 SQL 和样例数据
7. 保存视图

配置要求：
- JOIN 关系必须能够清晰解释业务含义
- 避免无意义的重复连表和字段冗余
- 优先保留真正会被维度、指标、字典或接口使用的字段
- 对存在歧义的同名字段，必须通过展示名或说明明确区分

#### 9.4.2 自定义 SQL 视图

适用于以下场景：
- 复杂统计逻辑难以通过可视化拖拽表达
- 需要对原始表做较多衍生处理或预聚合
- 需要快速固化一段稳定可复用的查询逻辑

配置要求：
- SQL 输出字段名应具备可读性
- 避免直接暴露大量无业务意义的中间字段
- 保存前必须执行至少一次预览
- 如该视图用于后续问数或接口生成，建议额外补字段展示名和说明

### 9.5 字段治理标准

视图字段建议至少治理以下内容：

| 配置项 | 标准要求 |
|------|------|
| 展示名称 | 建议补充，确保业务人员可理解 |
| 字段说明 | 对业务含义不直观的字段必须补充 |
| 可过滤 | 计划作为问数筛选条件或 API 参数的字段应开启 |
| 值域配置 | 固定枚举优先使用 `enum`；已有标准码表优先使用 `dict` |

治理建议：
- 时间字段、地区字段、组织字段、状态字段优先治理
- 若字段将用于外部接口参数，优先保证命名稳定、值域清晰
- 当前标准化文档仅把前端常用可配的 `enum`、`dict` 作为主口径，不把后端潜在扩展能力直接写成现场必配项

### 9.6 验证与验收要求

每个新建或修改后的视图，至少完成以下验证：
- 执行一次 SQL/数据预览
- 确认生成 SQL 可执行
- 确认样例数据正常返回
- 确认字段名称、展示名称、字段说明可读
- 确认该视图字段能够支撑后续维度、指标或字典配置

如该视图将作为重点问数入口，建议额外确认：
- 是否需要设置为默认视图
- 哪些字段需要开放为过滤字段
- 是否存在适合直接引用的字典字段

### 9.7 与下游模块依赖关系

视图配置完成后，通常会继续影响以下模块：

| 下游模块 | 依赖关系 |
|------|------|
| 维度管理 | 可直接基于视图字段配置维度 |
| 指标管理 | 可直接基于视图字段进行聚合或表达式计算 |
| 字典管理 | `引用视图` 类型字典直接依赖视图的值字段与标签字段 |
| 问数页面 | 查询上下文可绑定视图，影响推荐过滤字段与结果解释 |
| 生成接口 | 生成配置时会沿用查询使用的 `view_id`，并影响参数筛选质量 |

因此，建议现场实施时遵循“先视图、后维度/指标、再问数和接口”的顺序推进。

## 10. 字典配置标准

### 10.1 类型选择标准

| 字典类型 | 推荐使用场景 |
|------|------|
| 手动配置 | 枚举值固定、数量少、人工可控 |
| 引用视图 | 枚举值来源于主数据表，需动态维护 |
| 自动生成 | 字段值变化较快，需要周期性同步 |

### 10.2 配置建议

- 字典名称使用业务可理解名称
- 标签值必须与业务口径一致
- 同义词建议补充常见简称、别称、口语表达
- 用于接口参数下拉时，优先确保标签可读、值稳定
- 如使用 `引用视图` 类型，需确保关联视图已预览通过，且值字段、标签字段含义明确

## 11. 模型配置标准

### 11.1 基本要求

- 系统必须至少有一个“已启用 + 默认”的模型配置
- 配置完成后必须执行“测试连接”
- 若供应商要求 API Key 或 API 地址，必须按供应商要求填写

### 11.2 配置建议

| 项 | 建议 |
|------|------|
| 配置名称 | 体现环境和模型，如“生产-DeepSeek-chat” |
| 启用状态 | 仅启用当前可用模型，停用无效配置 |
| 默认模型 | 生产环境保持唯一默认模型 |
| 高级参数 | 无明确要求时使用默认值 |

### 11.3 验收标准

- 页面模型状态显示正常
- 默认模型可连通
- 可完成至少一次问数流程

## 12. 问数配置标准

当前页面支持“时间格式化配置”。

### 12.1 时间格式化标准

| 字段 | 标准要求 |
|------|------|
| 格式名称 | 与后端解析规则一致，如 `YYYY-MM-DD` |
| 显示标签 | 面向用户可读，如“按天”“按月” |
| 后缀标识 | 稳定唯一，如 `day`、`month`、`year` |
| 默认格式 | 仅允许一个默认值 |

### 12.2 推荐基础配置

| 格式名称 | 显示标签 | 后缀标识 | 是否推荐 |
|------|------|------|------|
| `YYYY-MM-DD` | 按天 | `day` | 是 |
| `YYYY-MM` | 按月 | `month` | 是 |
| `YYYY` | 按年 | `year` | 是 |

## 13. 查询结果生成接口标准

### 13.1 适用场景

当业务系统不直接接入问数页面，而是希望复用平台查询能力并通过标准接口返回结果时，可使用“生成接口”能力。

### 13.2 输出格式标准

- 目标格式示例必须为合法 JSON
- 最外层必须是数组
- 字段数量应以业务必要最小集为准
- 字段命名建议保持统一风格，避免同一接口中中英文混用

### 13.3 参数标准

- 优先从可过滤字段中选择
- 参数名应稳定、可复用、便于第三方系统理解
- 一个参数只表达一个业务含义，不建议多义复用
- 如参数存在枚举值，建议优先配置字典，便于调试和对接说明
- 如查询依赖视图，需优先确认该视图中的可过滤字段、值域配置和展示名称是否已整理完成，否则会直接影响 API 参数质量

### 13.4 交付标准

生成接口后，应至少完成以下动作：
1. 打开接口调试窗口
2. 执行一次成功调试
3. 复制接口端点并整理调用示例
4. 如结果不符合预期，执行一次“重新生成”并复测
5. 输出配套接口文档给对接方

## 14. 现场实施验收清单

### 14.1 基础验收

- [ ] 默认模型已配置并测试通过
- [ ] 数据源连接测试通过
- [ ] 关键物理表已同步
- [ ] 关键视图已完成分类、描述和至少一次预览
- [ ] 需要对外开放的视图字段已完成展示名、说明和可过滤治理
- [ ] 核心维度已配置完成
- [ ] 核心指标已配置完成
- [ ] 必要字典已配置完成
- [ ] 时间格式配置已完成且默认值正确

### 14.2 业务验收

- [ ] 查询结果字段名称符合业务理解
- [ ] 查询结果支持继续引用和条件调整

### 14.3 接口验收

- [ ] API 调试成功
- [ ] 请求参数、返回结构已与业务方确认

## 16. 结论

问数平台的实施成败，核心不在于单点功能是否存在，而在于数据源、语义层、模型和接口输出是否形成统一标准。建议现场实施时严格按照“先建模、后问数、再出接口”的顺序推进，并在每个阶段保留验收记录，便于后续复制到更多行业线项目。
