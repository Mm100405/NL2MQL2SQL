# 问数平台现场标准化部署文档

## 1. 部署目标

本文档面向现场实施，提供一套**尽量简单、可复制、可验收**的标准化部署方式。

**推荐方案：仅使用 Docker Compose 生产模式部署**。

原因：
- 步骤最少
- 前后端和数据库一起启动
- 适合现场环境快速落地
- 便于后续重启、升级和排障

> 本文档不展开本地开发模式，只说明现场标准部署。

---

## 2. 部署方式说明

本方案默认在**一台服务器**上部署以下 3 个服务：

| 服务 | 说明 | 默认宿主机端口 |
|------|------|------|
| frontend | 前端页面 | `18080` |
| backend | 后端服务 | `18011` |
| db | MySQL 数据库 | `13306` |

默认端口刻意避开 `80`、`8011`、`3306` 等常用端口，减少现场已有服务冲突。如现场已有统一网关或端口规划，可在 `.env` 中按需调整。

部署完成后，默认访问地址：

| 类型 | 地址 |
|------|------|
| 前端页面 | `http://服务器IP:18080` |
| 后端接口 | `http://服务器IP:18011` |
| Swagger 文档 | `http://服务器IP:18011/docs` |
| 健康检查 | `http://服务器IP:18011/health` |

---

## 3. 环境准备

部署前请确认：

1. 服务器已安装 **Docker**
2. 服务器已安装 **Docker Compose**
3. 建议使用较新的 Docker 版本（优先 Docker 20.10+ 或现场运维认可的新版 Docker Engine）
4. 已获取项目部署压缩包，例如 `NL2MQL2SQL-deploy.zip`
5. 服务器开放以下端口：
   - `18080`（前端页面默认端口）
   - `18011`（后端接口默认端口）
   - `13306`（仅在需要外部直连数据库时开放；否则可不对外开放）

部署前建议记录 Docker 与内核版本，便于排查兼容性问题：

```bash
docker version
docker info
uname -a
```

如果服务器是 Ubuntu 18.04 / Linux 4.15 / Docker 19.03 一类旧环境，可能在构建或启动容器时遇到 Docker seccomp 兼容问题，详见“10.8 旧 Docker / seccomp 兼容问题”。

## 4. 标准部署目录

部署时进入项目根目录：

```bash
NL2MQL2SQL/
```

关键文件：

| 文件 | 用途 |
|------|------|
| `.env.docker` | Docker 部署环境变量模板 |
| `docker-compose.yml` | 标准生产部署编排文件，兼容 Docker Compose v1/v2 |
| `frontend/.env.production` | 前端生产构建配置，默认使用相对接口地址 `/api/v1` |
| `backend/init.sql` | 数据库初始化脚本 |
| `backend/logs/` | 后端运行时日志目录，部署包中可不存在，容器启动后会自动创建 |
| `scripts/package-deploy.ps1` | Windows 本地生成现场部署压缩包脚本 |

## 5. 标准部署步骤

### 5.1 本地生成部署压缩包

在 Windows 本地 PowerShell 中进入项目根目录，执行：

```powershell
.\scripts\package-deploy.ps1
```

脚本会在项目同级目录生成 `NL2MQL2SQL-deploy-时间.zip`，并自动排除 `.git`、`.claude`、`.env`、`node_modules`、虚拟环境、缓存、日志、参考目录 `otherproj` 和历史压缩包等不应带到现场的内容。压缩包会保留项目目录结构，并保留 `frontend/.env.production`，确保前端生产包默认请求同域 `/api/v1`，不会请求开发机 `localhost`。

如需指定输出位置：

```powershell
.\scripts\package-deploy.ps1 -OutputPath "C:\Files\qoderProj\NL2MQL2SQL-deploy.zip"
```

将生成的压缩包上传到现场服务器并解压，后续命令均在解压后的 `NL2MQL2SQL/` 目录执行。

Linux 服务器示例：

```bash
mkdir -p NL2MQL2SQL
unzip NL2MQL2SQL-deploy.zip -d NL2MQL2SQL
cd NL2MQL2SQL
```

如果解压工具已经自动生成了项目目录，则进入实际包含 `docker-compose.yml`、`.env.docker`、`backend/`、`frontend/` 的目录即可。

部署包中不会包含现场 `.env` 文件，这是为了避免把本地密钥或数据库密码带到现场；`.env` 需要按下一步在服务器上生成。

### 5.2 复制环境变量文件

在项目根目录执行：

```bash
cp .env.docker .env
```

Windows 也可直接复制：

```bat
copy .env.docker .env
```

---

### 5.3 修改 `.env`

打开根目录 `.env`，至少修改以下 3 项：

```env
DB_PASSWORD=请改成现场数据库密码
SECRET_KEY=请改成现场使用的密钥
ENCRYPTION_KEY=请改成32位加密密钥
```

建议保留或按需确认以下配置：

```env
DB_USER=root
DB_NAME=nlqdb
DB_PORT=13306
MYSQL_IMAGE=docker.m.daocloud.io/library/mysql:8.0
FRONTEND_PORT=18080
BACKEND_PORT=18011
DEBUG=False
DISABLE_FASTAPI_THREADPOOL=false
```

### 5.4 配置项说明

| 配置项 | 是否必改 | 说明 |
|------|------|------|
| `DB_PASSWORD` | 是 | MySQL root 密码 |
| `SECRET_KEY` | 是 | 系统安全密钥 |
| `ENCRYPTION_KEY` | 是 | 数据加密密钥，建议固定保存 |
| `DB_USER` | 否 | 默认 `root`，用于后端连接数据库；MySQL 容器只配置 root 密码，不额外创建 root 普通用户 |
| `DB_NAME` | 否 | 默认 `nlqdb` |
| `DB_PORT` | 否 | 默认 `13306`，避开宿主机常见 MySQL 端口 `3306` |
| `MYSQL_IMAGE` | 否 | 默认 `docker.m.daocloud.io/library/mysql:8.0`，减少现场直连 Docker Hub 超时问题；也可改为内网镜像或已缓存版本 |
| `FRONTEND_PORT` | 否 | 默认 `18080`，避开常见 HTTP 端口 `80`；如仍冲突可改为 `18081` 等空闲端口 |
| `BACKEND_PORT` | 否 | 默认 `18011`，容器内后端仍监听 `8011` |
| `DEBUG` | 否 | 现场建议 `False` |
| `DISABLE_FASTAPI_THREADPOOL` | 否 | 默认 `false`，保留 FastAPI 线程池，避免外部数据源连接/同步阻塞所有接口 |

> `ENCRYPTION_KEY` 建议使用固定值，不要频繁更换，否则可能影响已保存的加密配置。

---

### 5.5 启动服务

在项目根目录执行：

```bash
docker-compose build
docker-compose up -d
```

如果服务器使用 Docker Compose v2，也可以使用等价命令：

```bash
docker compose build
docker compose up -d
```

启动时后端会自动执行数据库迁移并补齐当前版本需要的表结构。如果迁移失败，后端容器会启动失败，应先查看后端日志处理根因，不要忽略后继续验收。

如果 `docker-compose build` 或 `docker-compose up -d` 报错包含以下内容：

```text
error loading seccomp filter into kernel: errno 524
```

说明当前服务器 Docker / 内核存在 seccomp 兼容问题，不是应用代码或部署包结构问题。应优先联系现场运维升级 Docker Engine 或内核；若短期不能升级，按“10.8 旧 Docker / seccomp 兼容问题”处理。

如果现场希望直接使用脚本，也可以执行：

```bat
docker-start.bat
```

然后选择：

```text
2) 生产环境（优化镜像）
```

> 现场标准化建议优先使用 `docker-compose build` + `docker-compose up -d`，命令更直接，也更方便写入实施手册。

## 6. 部署完成后验证

### 6.1 查看容器状态

```bash
docker-compose ps
```

Docker Compose v2 环境可执行 `docker compose ps`。

正常情况下应看到：
- `db` 运行中
- `backend` 运行中，且健康检查通过
- `frontend` 运行中

如果 `backend` 反复重启，优先查看 `docker-compose logs -f backend`，通常是数据库连接或迁移失败。


期望返回：


浏览器访问：

```text
http://服务器IP:18080
```

- 左侧可见新建对话、历史对话

期望结果：

## 7. 首次上线后必须完成的初始化配置

系统部署成功后，还需要完成一次平台初始化，否则前端虽然能打开，但问数功能可能无法使用。

### 7.1 配置模型

进入：

```text
管理中心 -> 系统配置 -> 模型配置
```

至少完成：
1. 新增一个模型配置
2. 填写供应商、模型名、API Key / API 地址
3. 点击“测试连接”
4. 设为默认模型

> **这是问数功能可用的前提。** 如果不配置模型，查询页面会提示模型不可用。

### 7.2 配置数据源

进入：

```text
管理中心 -> 数据管理 -> 数据源管理
```

至少完成：
1. 新增数据源
2. 填写数据库连接信息
3. 点击“测试连接”
4. 状态显示为“正常”

### 7.3 验证问数链路

建议至少完成一次完整验证：

1. 打开首页问数页面
2. 输入一个简单问题
3. 确认能返回结果
4. 确认历史对话可正常保存和恢复

## 8. 日常运维命令

### 8.1 查看状态

```bash
docker-compose ps
```

### 8.2 查看日志

```bash
docker-compose logs -f
```

只看后端日志：

```bash
docker-compose logs -f backend
```

只看前端日志：

```bash
docker-compose logs -f frontend
```

只看数据库日志：

```bash
docker-compose logs -f db
```

### 8.3 重启服务

```bash
docker-compose restart
```

仅重启后端：

```bash
docker-compose restart backend
```

### 8.4 停止服务

```bash
docker-compose down
```

> `docker-compose down` 会停止容器，但**不会删除数据库数据卷**。

### 8.5 禁止误删数据

不要在现场随意执行：

```bash
docker-compose down -v
```

该命令会删除数据卷，可能导致数据库数据被清空。

如果需要现场升级代码，建议使用以下标准步骤：

1. 替换项目代码目录
2. 保留原 `.env`
3. 在项目根目录重新执行：

```bash
docker-compose build
docker-compose up -d
```

4. 重新访问：
   - 前端页面
   - `/health`
   - `/docs`

> 后端启动时会自动检查数据库并执行迁移，无需手工执行 Alembic 命令。

## 10. 常见问题处理

### 10.1 前端打不开

排查顺序：
1. `docker-compose ps` 查看 `frontend` 是否运行
2. 检查 `FRONTEND_PORT` 端口是否被占用；如 `18080` 被占用，可在 `.env` 中改为 `FRONTEND_PORT=18081` 后重新执行 `docker-compose up -d`
3. 查看前端日志：

```bash
docker-compose logs -f frontend
```

---

### 10.2 `/health` 不通

排查顺序：
1. `backend` 容器是否运行
2. `18011` 端口是否开放
3. 查看后端日志：

```bash
docker-compose logs -f backend
```

---

### 10.3 页面能打开，但无法问数

通常是以下原因：
- 未配置模型
- 默认模型未启用
- 模型连接测试失败
- 数据源未配置或无可用语义层配置

优先检查：

```text
管理中心 -> 系统配置 -> 模型配置
```

---

### 10.4 数据库启动失败

优先检查：
- `.env` 中 `DB_PASSWORD` 是否配置正确
- `13306` 端口是否冲突
- 是否误执行过 `docker-compose down -v`

查看日志：

```bash
docker-compose logs -f db
```

---

### 10.5 页面请求到了 `localhost:8011`

如果浏览器 F12 看到前端请求 `http://localhost:8011`，说明前端生产构建没有读取到 `frontend/.env.production`。

处理方式：
1. 确认部署目录存在 `frontend/.env.production`
2. 文件内容应包含：

```env
VITE_API_BASE_URL=/api/v1
```

3. 重新构建并启动前端：

```bash
docker-compose build frontend
docker-compose up -d frontend
```

---

### 10.6 后端提示缺少 `views`、`field_dictionaries` 等表

后端启动时会自动执行 Alembic 迁移并补齐当前版本需要的表结构。若仍出现缺表：

1. 查看后端启动日志：

```bash
docker-compose logs -f backend
```

2. 确认不是旧版本部署包或旧镜像：

```bash
docker-compose build backend
docker-compose up -d backend
```

3. 不要手工删除数据库卷，也不要执行 `docker-compose down -v`，避免清空现场数据。

---

### 10.7 模型测试或接口返回 `can't start new thread`

如果模型连接测试返回“无法连接到服务器”，后端日志或直接调试中出现 `can't start new thread`，通常是现场 Docker 容器的进程/线程配额过低。

标准 `docker-compose.yml` 已为 `backend` 配置：

```yaml
ulimits:
  nproc: 65535
  nofile:
    soft: 65535
    hard: 65535
```

处理步骤：

```bash
docker-compose up -d --force-recreate backend
```

然后进入容器检查：

```bash
docker-compose exec backend sh -c "ulimit -u && python - <<'PY'
import threading, time
t = threading.Thread(target=lambda: time.sleep(0.1))
t.start()
t.join()
print('thread ok')
PY"
```

如果仍失败，说明服务器或 Docker 守护进程层面限制了容器线程数，需要现场运维放开容器进程数限制后再重建后端容器。

---

### 10.8 旧 Docker / seccomp 兼容问题

如果现场服务器使用较旧的 Docker / 内核组合，例如：

```text
Docker Server Version: 19.03.x
Ubuntu: 18.04.x
Kernel: 4.15.x
```

执行以下命令时可能失败：

```bash
docker-compose build
docker-compose up -d
docker-compose exec backend sh
```

典型错误如下：

```text
OCI runtime create failed: container_linux.go:349: starting container process caused "error loading seccomp filter into kernel: errno 524"
```

处理原则：

1. **优先推荐升级 Docker Engine 或内核**。这是最干净、最可复制的处理方式，升级后再重新执行标准流程：

   ```bash
   docker-compose build
   docker-compose up -d
   ```

2. 如果现场短期不能升级，可在项目根目录新增 `docker-compose.override.yml`，对受影响服务临时关闭默认 seccomp 限制：

   ```yaml
   version: '3.7'

   services:
     db:
       security_opt:
         - seccomp=unconfined
     backend:
       security_opt:
         - seccomp=unconfined
   ```

   然后重新启动：

   ```bash
   docker-compose up -d db backend
   ```

3. 注意：上述 `security_opt` 主要解决**容器启动/重建**时的 seccomp 问题，不一定能解决**镜像构建阶段**的 `RUN` 步骤失败。部分旧 Docker 版本不支持 `docker build --security-opt`，此时即使有 override，`docker-compose build backend` 仍可能失败。

   判断方式：

   ```bash
   docker run --rm docker.m.daocloud.io/library/python:3.11-slim-bullseye python --version
   docker run --rm --security-opt seccomp=unconfined docker.m.daocloud.io/library/python:3.11-slim-bullseye python --version
   ```

   如果第一条失败但第二条成功，说明容器运行必须带 `seccomp=unconfined`。

4. 如果 build 阶段仍失败，应选择以下任一方式：
   - 由现场运维升级 Docker / 内核后回到标准流程；
   - 在其他兼容环境预构建后端和前端镜像，现场只 `docker load` 镜像并执行 `docker-compose up -d`；
   - 在应急场景下，使用 `docker run --security-opt seccomp=unconfined` 启动基础镜像，`docker cp` 项目代码进去，安装依赖/构建前端后 `docker commit` 成本地镜像，再把 `docker-compose.yml` 的 `build` 改为 `image` 引用本地镜像。

   应急流程示意：

   ```bash
   # 后端：python 基础镜像 -> 安装 requirements -> commit 为 nl2mql2sql_backend:local
   docker run -dit --security-opt seccomp=unconfined --name nl2mql2sql-backend-build -w /app docker.m.daocloud.io/library/python:3.11-slim-bullseye sh
   docker cp backend/. nl2mql2sql-backend-build:/app/
   docker exec nl2mql2sql-backend-build sh -lc "pip install --upgrade pip --progress-bar off -i https://pypi.tuna.tsinghua.edu.cn/simple && pip install --progress-bar off --timeout 120 --retries 10 -i https://pypi.tuna.tsinghua.edu.cn/simple -r requirements.txt && mkdir -p logs"
   docker commit --change 'WORKDIR /app' --change 'EXPOSE 8011' --change 'CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8011", "--loop", "asyncio", "--http", "h11"]' nl2mql2sql-backend-build nl2mql2sql_backend:local
   docker rm -f nl2mql2sql-backend-build

   # 前端：node 基础镜像构建 dist，再拷贝到 nginx 镜像并 commit
   docker run -dit --security-opt seccomp=unconfined --name nl2mql2sql-frontend-build -w /app docker.m.daocloud.io/library/node:20-alpine3.22 sh
   docker cp frontend/. nl2mql2sql-frontend-build:/app/
   docker exec nl2mql2sql-frontend-build sh -lc "npm config set registry https://registry.npmmirror.com && npm ci && npx vite build"
   docker run -dit --security-opt seccomp=unconfined --name nl2mql2sql-nginx-build docker.m.daocloud.io/library/nginx:alpine sh
   docker cp frontend/nginx.conf nl2mql2sql-nginx-build:/etc/nginx/conf.d/default.conf
   docker cp nl2mql2sql-frontend-build:/app/dist /tmp/nl2mql2sql-dist
   docker cp /tmp/nl2mql2sql-dist/. nl2mql2sql-nginx-build:/usr/share/nginx/html/
   docker commit --change 'EXPOSE 80' --change 'CMD ["nginx", "-g", "daemon off;"]' nl2mql2sql-nginx-build nl2mql2sql_frontend:local
   docker rm -f nl2mql2sql-frontend-build nl2mql2sql-nginx-build
   rm -rf /tmp/nl2mql2sql-dist
   ```

   使用本地镜像时，将 `docker-compose.yml` 中 backend/frontend 的 `build` 替换为：

   ```yaml
   backend:
     image: nl2mql2sql_backend:local

   frontend:
     image: nl2mql2sql_frontend:local
   ```

   并为受影响服务添加：

   ```yaml
   security_opt:
     - seccomp=unconfined
   ```

5. 使用 `seccomp=unconfined` 会弱化容器隔离，仅建议作为旧现场环境的临时兼容方案；能升级 Docker / 内核时，应优先升级并移除该 override。

## 12. 推荐现场操作口径

现场实施时，统一按以下口径执行：

1. **只用 Docker Compose 生产模式部署**
2. **统一改 `.env` 三个关键项：数据库密码、安全密钥、加密密钥**
3. **统一用 `/health`、首页、`/docs` 做验收**
4. **统一先配模型，再做问数验证**
5. **禁止现场随意执行 `down -v`**

这样可以把部署方式、排障方式和验收方式都统一下来，方便复制到多个项目现场。
